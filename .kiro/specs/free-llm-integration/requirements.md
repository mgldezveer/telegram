# Requirements Document: Free LLM Integration

## Introduction

Интеграция бесплатных LLM API для системы вайбкодинга и генерации контента. Система должна поддерживать несколько бесплатных провайдеров с автоматическим переключением при достижении лимитов.

## Glossary

- **LLM (Large Language Model)**: Большая языковая модель для генерации текста
- **API Provider**: Провайдер API для доступа к LLM
- **Rate Limit**: Ограничение количества запросов
- **Fallback**: Резервный вариант при недоступности основного сервиса
- **Token**: Единица измерения текста для LLM
- **Prompt**: Запрос к LLM для генерации текста

## Requirements

### Requirement 1: Поддержка множественных бесплатных провайдеров

**User Story:** Как разработчик, я хочу использовать несколько бесплатных LLM провайдеров, чтобы не зависеть от одного сервиса и обходить лимиты.

#### Acceptance Criteria

1. WHEN система инициализируется, THE system SHALL загрузить конфигурацию всех доступных бесплатных провайдеров
2. WHEN провайдер настроен, THE system SHALL проверить доступность API ключа
3. WHEN провайдер недоступен, THE system SHALL автоматически переключиться на следующий доступный провайдер
4. WHEN все провайдеры недоступны, THE system SHALL вернуть информативное сообщение об ошибке
5. THE system SHALL поддерживать минимум 3 бесплатных провайдера (Groq, Gemini, Hugging Face)

### Requirement 2: Groq API Integration

**User Story:** Как пользователь, я хочу использовать Groq API для быстрой генерации контента, чтобы получать результаты с минимальной задержкой.

#### Acceptance Criteria

1. WHEN Groq API ключ предоставлен, THE system SHALL инициализировать Groq клиент
2. WHEN запрос отправлен к Groq, THE system SHALL использовать модель Llama 3 или Mixtral
3. WHEN достигнут rate limit, THE system SHALL переключиться на другой провайдер
4. WHEN запрос успешен, THE system SHALL вернуть сгенерированный текст
5. THE system SHALL логировать использование токенов для мониторинга лимитов

### Requirement 3: Google Gemini Integration

**User Story:** Как пользователь, я хочу использовать Google Gemini API для генерации контента, чтобы иметь доступ к качественной модели бесплатно.

#### Acceptance Criteria

1. WHEN Gemini API ключ предоставлен, THE system SHALL инициализировать Gemini клиент
2. WHEN запрос отправлен к Gemini, THE system SHALL использовать модель gemini-pro
3. WHEN достигнут дневной лимит, THE system SHALL переключиться на другой провайдер
4. WHEN запрос успешен, THE system SHALL вернуть сгенерированный текст
5. THE system SHALL обрабатывать safety settings для контроля контента

### Requirement 4: Hugging Face Integration

**User Story:** Как пользователь, я хочу использовать Hugging Face Inference API для генерации контента, чтобы иметь доступ к открытым моделям.

#### Acceptance Criteria

1. WHEN Hugging Face API ключ предоставлен, THE system SHALL инициализировать HF клиент
2. WHEN запрос отправлен к HF, THE system SHALL использовать доступные бесплатные модели
3. WHEN модель недоступна, THE system SHALL попробовать альтернативную модель
4. WHEN запрос успешен, THE system SHALL вернуть сгенерированный текст
5. THE system SHALL кэшировать результаты для оптимизации использования

### Requirement 5: Автоматическое управление лимитами

**User Story:** Как администратор, я хочу автоматически отслеживать использование API, чтобы не превышать бесплатные лимиты.

#### Acceptance Criteria

1. WHEN запрос выполнен, THE system SHALL записать количество использованных токенов
2. WHEN приближается лимит провайдера, THE system SHALL отправить предупреждение
3. WHEN лимит достигнут, THE system SHALL автоматически переключиться на другой провайдер
4. THE system SHALL сбрасывать счетчики лимитов согласно периоду провайдера (час/день/месяц)
5. THE system SHALL предоставлять статистику использования по каждому провайдеру

### Requirement 6: Кэширование и оптимизация

**User Story:** Как пользователь, я хочу минимизировать количество API запросов, чтобы экономить бесплатные лимиты.

#### Acceptance Criteria

1. WHEN идентичный запрос отправлен повторно, THE system SHALL вернуть кэшированный результат
2. WHEN кэш заполнен, THE system SHALL удалять старые записи по алгоритму LRU
3. THE system SHALL кэшировать результаты на минимум 1 час
4. WHEN промпт изменен незначительно, THE system SHALL использовать семантическое кэширование
5. THE system SHALL предоставлять статистику попаданий в кэш

### Requirement 7: Обработка ошибок и retry логика

**User Story:** Как пользователь, я хочу надежную систему генерации, чтобы временные сбои не прерывали работу.

#### Acceptance Criteria

1. WHEN API запрос не удался, THE system SHALL повторить запрос до 3 раз с экспоненциальной задержкой
2. WHEN провайдер вернул ошибку rate limit, THE system SHALL немедленно переключиться на другой провайдер
3. WHEN все retry попытки исчерпаны, THE system SHALL переключиться на следующий провайдер
4. WHEN все провайдеры недоступны, THE system SHALL вернуть понятное сообщение об ошибке
5. THE system SHALL логировать все ошибки с контекстом для отладки

### Requirement 8: Конфигурация и управление

**User Story:** Как администратор, я хочу легко настраивать провайдеры через переменные окружения, чтобы не изменять код.

#### Acceptance Criteria

1. THE system SHALL загружать API ключи из переменных окружения
2. THE system SHALL поддерживать приоритизацию провайдеров через конфигурацию
3. WHEN провайдер отключен в конфигурации, THE system SHALL пропускать его
4. THE system SHALL валидировать конфигурацию при запуске
5. THE system SHALL предоставлять команду для проверки статуса всех провайдеров

### Requirement 9: Мониторинг и аналитика

**User Story:** Как администратор, я хочу видеть статистику использования LLM, чтобы оптимизировать расходы и производительность.

#### Acceptance Criteria

1. THE system SHALL отслеживать количество запросов к каждому провайдеру
2. THE system SHALL отслеживать среднее время ответа каждого провайдера
3. THE system SHALL отслеживать количество ошибок по провайдерам
4. THE system SHALL предоставлять dashboard с метриками использования
5. THE system SHALL экспортировать метрики в Prometheus формате

### Requirement 10: Интеграция с вайбкодингом

**User Story:** Как пользователь вайбкодинга, я хочу использовать реальный LLM вместо заглушек, чтобы получать качественный контент.

#### Acceptance Criteria

1. WHEN пользователь выбирает роль вайбкодинга, THE system SHALL использовать LLM для генерации
2. WHEN генерация запущена, THE system SHALL показывать индикатор загрузки
3. WHEN генерация завершена, THE system SHALL отформатировать результат для Telegram
4. WHEN генерация не удалась, THE system SHALL показать понятное сообщение об ошибке
5. THE system SHALL сохранять историю генераций для каждого пользователя

## Priority

   - Requirement 1: Поддержка множественных провайдеров
   - Requirement 2: Groq API Integration

   - Requirement 7: Обработка ошибок

2. **Средний приоритет:**
   - Requirement 3: Google Gemini Integration
   - Requirement 6: Кэширование
   - Requirement 8: Конфигурация
   - Requirement 10: Интеграция с вайбкодингом

3. **Низкий приоритет:**
   - Requirement 4: Hugging Face Integration
   - Requirement 9: Мониторинг и аналитика
